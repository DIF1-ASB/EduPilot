# Онлайн-контрольные и связные конспекты

Эта версия подготовлена для локальной проверки. Она не означает публикацию на VPS или смену рабочего ИИ-провайдера. Существующие аккаунты, чаты, материалы, группы, назначения и попытки не нужно удалять, пересоздавать или импортировать заново.

## Что изменилось

Преподаватель задаёт тему, предмет, класс и уточнения. Фоновая задача сохраняет черновик теста: по умолчанию десять вопросов, четыре варианта, один правильный ответ, один балл. Преподаватель проверяет содержание и ключи, подтверждает их и выдаёт работу своей группе. Изменение вопроса сбрасывает подтверждение. По умолчанию разрешена одна попытка, решения скрыты до разрешения преподавателя. Скачивание контрольных Word/PDF отключено, включая контрольные на базе рабочего листа. Самостоятельные рабочие листы и домашние задания сохраняют экспорт.

Ученик выбирает ответы на сайте. Порядок вариантов сохраняется для каждой попытки; перезагрузка не меняет ни порядок, ни срок окончания. Пустая ручная отправка не раскрывает решения. Оценка определяется ключами, без обращения к ИИ. Результаты контрольных показаны отдельно от тренировок: учитывается последняя завершённая попытка каждого ученика по каждому назначению. Ожидающая ручной проверки работа не считается нулём. Прежние смешанные задания продолжают работать.

Новые конспекты сохраняют связный текст, заголовки, примеры и формулы. Ориентир генерации — 700–1000 слов, принимается 700–1100; это примерно две-три страницы, а не гарантия точного объёма. Старые форматы не преобразуются автоматически. Word/PDF остаются для конспектов. Формулы в скачанных документах — изображения, а не редактируемые уравнения Word; окружающий текст редактируется. В облачной сборке новый экспорт формул явно недоступен, старые экспорты не отключены.

## Изолированная приёмка

Нужен Node >=22.13 и совместимая с ним native-сборка better-sqlite3. Не переключайте Node, оставляя бинарный модуль от другой версии. Установите зависимости через штатный install workflow проекта. Не запускайте setup с адресом настоящей базы для приёмки.

В этом Windows-checkout для приёмки сохранён проверенный Node 22.23.3 в игнорируемом `work/runtime/node-v22.23.3-win-x64`; better-sqlite3 собран под него. Системный Node не заменялся. Перед командами ниже в **каждом** терминале из корня проекта можно задать `$env:PATH="$PWD\work\runtime\node-v22.23.3-win-x64;$env:PATH"` и проверить `node --version`. Это меняет только текущий терминал. Этот локальный runtime не входит в Git: в другой копии проекта нужен обычный Node >=22.13 и установка совместимых зависимостей.

1. Выполните `npm test`, `npm run typecheck`, `npm run build` и `npm run sites:build`.
2. В отдельном терминале из корня репозитория запустите `node --import tsx e2e/local-server.ts`.
3. В терминале проверки задайте `EDUPILOT_TEST_URL=http://127.0.0.1:3400`, затем `npm run test:e2e`. На Windows PowerShell переменная задаётся как `$env:EDUPILOT_TEST_URL='http://127.0.0.1:3400'`.
4. После проверки остановите harness сочетанием Ctrl+C. Он завершает запущенные им приложение и worker и удаляет только свою временную тестовую базу. Скриншоты и загрузки находятся в `output/playwright`.

Harness сам создаёт новую временную SQLite, применяет миграции, запускает приложение на 3400, отдельный worker и синтетический локальный ИИ на 3401. Он не открывает прежнюю базу и не использует настоящий API-ключ. Порты должны быть свободны: не останавливайте чужие процессы для их освобождения. Конфигурация E2E отклоняет удалённые адреса и старый параметр удалённого QA. Для старых конспектов используется CLI-мост только к проверенной синтетической базе, не HTTP-обход авторизации.

Фикстуры проверяют интерфейс и контракты, но не качество реальной модели. Ранее проведённая адаптационная проверка Nemotron выявила содержательные ошибки даже при корректном JSON. Новый провайдер для рабочего сайта не выбран; новые платные/внешние оценочные запросы не запускаются автоматически из CI. До выбора модели отдельно проверьте условия сервиса, качество на предметных примерах и бюджет.

## Фоновые задачи на Node

Функция по умолчанию выключена: `GENERATION_JOBS_ENABLED=false`. Для отдельного локального экземпляра с подходящим провайдером задайте `GENERATION_JOBS_ENABLED=true`, затем отдельно запустите `npm run generation:worker`. Для одного ограниченного прохода: `npm run generation:worker -- --once`. Остановка — Ctrl+C или SIGTERM. На сервер пока ничего устанавливать не требуется; systemd-файл в `scripts/ops` является шаблоном, а не активной службой.

Приложение и worker должны использовать одну базу, одинаковую конфигурацию провайдера и одного служебного пользователя. Не храните ключ в репозитории, браузере, логах или командной строке. Лимиты: один активный job пользователя, максимум два занятых upstream-слота, один repair, 120 секунд на запрос, общий срок 300 секунд. Отменённый вызов удерживает слот до завершения/прерывания или восстановления lease. После сбоя истёкшие задачи становятся ошибкой с возможностью нового запуска, без скрытого повторного запроса к провайдеру. Готовый материал никогда не выдаётся группе автоматически.

## Сохранность данных перед будущим обновлением

Публикация требует отдельного разрешения. Перед ней остановите выдачу новых записей на время согласованного снимка, сделайте согласованную резервную копию SQLite и private-storage, сохраните серверную конфигурацию отдельно и проверьте восстановление на временной копии. Для работающей SQLite используйте штатный online backup, не обычное копирование одного файла без учёта WAL. Не подменяйте рабочую базу локальной и не применяйте destructive reset/db push --force-reset.

Миграции этого этапа добавляют GenerationJob, AssessmentAttempt.optionOrderJson и Assignment.contextJson. Старые поля не удаляются. Сравните HMAC manifest всех прежних таблиц/полей и вложений до/после миграций на копии; новые поля не входят в прежний manifest. Только после успешной репетиции согласуйте обновление кода, миграций и запуск worker. При необходимости отката учитывайте, что старый код не понимает новые статьи: одного отката кода недостаточно без согласованного плана доступа к новым материалам. Никогда не восстанавливайте старую резервную копию поверх более новых пользовательских записей без явного решения владельца.

Исторические назначения, созданные до сохранения предметного контекста, обозначаются как использующие текущие метаданные исходного материала. Для новых назначений контекст фиксируется при выдаче. Историю нельзя искусственно достроить задним числом.
